# FILPRO V2 — export/import et configuration de déploiement

Demandes directes David du 25/10/2026 : exporter une configuration à fournir avec le pack PROD, appliquée automatiquement au premier lancement dans la configuration AppData ; export ET import manuels doivent aussi être possibles. Ces fonctions font partie du développement V2 avant commit/push sources, puis tests. FULL SPARK.

## Constat de source
V1 : Get-FilproPrefsPath dans wad/FILPRO.ps1 utilise %LOCALAPPDATA%\FILPRO\filpro.prefs.json. La configuration générale FILPRO.config.json de V1 est distincte et peut être lue près du programme. V2 actuelle : src/Filpro.App/AppPaths.cs résout %LOCALAPPDATA%\FILPRO. Respecter les propriétaires de préférences/configuration existants et leur migration ; ne pas fusionner aveuglément tous les fichiers en un nouveau format. Vérifier le code au moment de l’implémentation.

## Fonctions attendues
1. Paramètres : « Exporter la configuration » produit un JSON portable versionné après choix de destination ; « Importer une configuration » lit le même format, valide et présente un aperçu des changements puis applique sur confirmation. Le premier lancement sait consommer automatiquement un exemplaire valide fourni avec le PROD.
2. Export contrôlé des réglages de l’application, options de sauvegarde/restauration, sources de mise à jour, modèles/préréglages et autres paramètres partageables réellement présents. Liste explicite de champs. Aucun mot de passe, token, clé de chiffrement/DPAPI, cookie/SSO, identité/SID sélectionné, historique, journal ou données sauvegardées. Des chemins de stockage configurés peuvent être inclus comme paramètres mais n’impliquent aucun accès réseau ou lancement automatique. Aucune capacité Admin, commande/script ou autorisation ne vient du JSON.
3. Adapter le nom à une convention unique documentée (proposition FILPRO.bootstrap.json près de FILPRO.exe). Localisation précise liée au dossier du programme, pas recherche dans le répertoire courant ou scan de partages. Source lue uniquement ; le pack doit rester utilisable sur USB ou emplacement en lecture seule.
4. Premier lancement par utilisateur : si aucune configuration utilisateur normale n’existe, valider puis initialiser atomiquement les fichiers attendus sous le même %LOCALAPPDATA%\FILPRO. Si une configuration V1/V2 existe, préserver ses octets et utiliser la migration prévue ; ne pas réappliquer la configuration de distribution à chaque lancement ou mise à jour. Une trace d’import identifie schéma/hash/résultat, jamais les secrets. Deux lancements concurrents ne doivent pas s’écraser.
5. Import manuel sur une configuration existante : aperçu lisible, confirmation, sauvegarde récupérable, validation de fraîcheur depuis l’aperçu puis écriture atomique. Annulation = aucun changement. Les champs absents ne suppriment pas les réglages existants par défaut. Ne pas importer un schéma futur, un autre produit, un JSON malformé/doublonné/trop volumineux ou des champs interdits. Aucun effet système/backup/restore/update déclenché par import seul.
6. JSON de déploiement invalide/incompatible au premier lancement : message compréhensible, application utilisable avec réglages sûrs, aucune écriture partielle ni succès fictif. Préserver tout fichier préexistant. Aucun contournement de la validation pour l’import automatique.
7. Intégrer réellement au contrat des packs PROD/DEV et à l’outil de fabrication : fichier optionnel de configuration fourni via une option d’empaquetage qui génère des manifestes/hashes cohérents, ou mécanisme externe de bootstrap explicitement déclaré. Ne pas affaiblir le contrôle d’intégrité exact du pack pour tolérer arbitrairement des fichiers ajoutés. Expliquer comment joindre l’export au pack et où il est importé. Ne pas copier la configuration privée du développeur lors de la fabrication.
8. Démo : export marqué fictif si autorisé ; import/réinitialisation n’affectent que son magasin dédié. L’import automatique du pack ne doit pas écraser le contexte normal en passant par la démo.

## Décision prioritaire suivante de David : nouvelle version et configuration existante

David précise : « on force le remplacement de l’ancienne conf au lancement du new version, ou on propose remplacement au moin au premier start ». Retenir la proposition explicite, qui répond à cette demande sans écrasement silencieux. Cette section remplace la règle antérieure qui ignorait simplement le fichier fourni lorsqu’une configuration existait.

- Profil neuf : import automatique validé inchangé.
- Configuration existante au premier lancement d’une nouvelle version avec un fichier de configuration fourni valide : afficher l’aperçu des changements et proposer « Appliquer la configuration fournie » / « Garder mes réglages ». Ne pas appliquer en arrière-plan. L’utilisateur doit pouvoir continuer avec ses réglages actuels.
- Si application choisie : remplacer les réglages exportables concernés selon le contrat de l’export, avec sauvegarde récupérable, contrôle de fraîcheur et écriture atomique. L’aperçu distingue valeurs remplacées, supprimées/réinitialisées et conservées. Aucun remplacement de secrets, identités, profils, magasins, données ou historiques. Ne pas transformer le bouton de remplacement en fusion silencieuse contraire à l’aperçu.
- Mémoriser la décision pour l’utilisateur et l’identité vérifiée de version/pack + hash du fichier fourni. Aucun dialogue en boucle au lancement suivant pour la même proposition ; une nouvelle version/configuration justifie une nouvelle proposition. Une annulation ne marque pas un import réussi.
- Fichier absent : conserver les réglages avec migrations prévues ; aucun reset. Invalide/incompatible : conserver les octets actuels, avertir clairement, aucun remplacement ni succès fictif.
- Un échec d’écriture ou un contexte modifié après l’aperçu conserve/restaure l’ancienne configuration, sans faux reçu. Ne pas marquer accepté avant réussite.
- Import manuel reste disponible dans Paramètres, même après avoir choisi de garder les réglages. La démo utilise uniquement son magasin fictif.
- Ajouter aux contrôles ciblés après développement : première proposition nouvelle version, choix garder/remplacer, sauvegarde/restauration, second lancement silencieux, nouvelle version/hash, invalidité, annulation et concurrence.

## Dernière précision David : « Définir comme configuration par défaut »

Parcours principal demandé : configurer le logiciel dans son dossier PROD, cliquer « Définir comme configuration par défaut », puis diffuser ce dossier/pack avec ces réglages par défaut. Ne pas obliger à exporter manuellement un fichier puis le replacer soi-même. Les fonctions export/import restent disponibles comme options complémentaires.

- Ajouter ce bouton dans Paramètres. Il capture les paramètres partageables actuels dans le même contrat versionné que l’export/import, présente un résumé et écrit atomiquement le fichier de configuration par défaut dans le dossier distribuable du logiciel. Aucun secret, identité, historique, donnée métier ou clé n’est exporté. Aucun pouvoir supplémentaire ni opération automatique n’est accordé par cette configuration.
- Le bouton remplace la précédente configuration de distribution après confirmation et sauvegarde récupérable. Il ne réinitialise pas les préférences courantes de l’opérateur. Les réglages restent normalement utilisés depuis son AppData.
- Le fichier écrit est celui réellement consommé par le bootstrap : nouveaux utilisateurs = import automatique ; utilisateurs existants = proposition garder/appliquer selon identité du pack/version et empreinte de la configuration fournie. Une nouvelle empreinte des défauts doit permettre une nouvelle proposition une seule fois, même si la version affichée du logiciel n’a pas changé.
- Prévoir un traitement explicite du dossier PROD non accessible en écriture : message compréhensible et possibilité de choisir une copie/destination distribuable. Ne pas écrire silencieusement uniquement dans AppData, ne pas élever les droits sans nécessité, ne pas modifier un partage de mises à jour configuré qui reste en lecture seule.
- Compatible avec le contrat d’intégrité des packs : fichier de paramètres de déploiement optionnel explicitement distinct des binaires gérés et validé selon son schéma ; ou fabrication du pack configuré avec inventaire cohérent. Ne pas désactiver la vérification des binaires, ne pas forger de signature éditeur. Une configuration locale modifiable n’est pas une signature d’authenticité. Le flux distribué doit fonctionner réellement après copie/réarchivage.
- Après succès, afficher le chemin écrit et une confirmation claire que le dossier peut être diffusé avec ces défauts. Une erreur ne doit jamais annoncer que le pack est configuré. Documenter ce parcours simple dans le guide de diffusion.
- Depuis la démo : interdire la modification des défauts du vrai dossier PROD ; simuler le bouton dans l’espace fictif, résultat clairement marqué démonstration.
- Préparer les petits contrôles ciblés : modifier les réglages, définir les défauts, copier/réarchiver le dossier configuré, ouvrir avec profil neuf puis profil existant, vérifier les valeurs et le choix mémorisé ; secrets absents, dossier lecture seule, échec atomique, intégrité des binaires inchangée et isolation de la démo. Exécution après développement, VM seulement pour les scénarios critiques.
